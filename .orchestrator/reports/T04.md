# T04: route every Gemini call through the key pool (the parallel generate loop)

## Implemented
- `backend/app/stepper.py`:
  - Added `keypool` to the existing `from app.engine import ...` line.
  - New module-level helper `_step_result(status, *, item=None, next_delay_ms=None,
    retry_after_ms=None, next_step_ms=0, key_hint=None, lanes=1, job)` that builds the full
    return dict (including `remaining`/`done`/`failed` from `job`) so no `generate_step`
    return path can forget `next_step_ms`/`key_hint`/`lanes`. Every `return {...}` in
    `generate_step` now goes through it.
  - `generate_step(db, job, shop, user: User)` — signature changed from `api_key: str` to
    `user: User`; docstring explains the pace gate is now a per-key lease, that
    `next_step_ms` is the per-LANE wait vs. `next_delay_ms` the per-KEY pace, and that an
    AuthFailure disables one key rather than the job.
  - Old "Step 2 pace gate" (read one key's `PaceState`) replaced by the lease block exactly
    as specified: `keypool.lane_count(enabled_count)`, `keypool.lease(db, user.id)`; on
    `None` falls back to `keypool.wait_ms` — `None` (no enabled key at all) fails the job,
    otherwise returns `waiting` with the pool-wide wait. On success, `job.api_key_hash` is
    set to the leased key's hash (now genuinely "last key used", not "first").
  - The `item is None` branch (recovered / inflight / complete sub-branches) now calls
    `keypool.release_now(db, key_hash)` first, before any of the existing logic, since no
    item was claimed with the leased key.
  - The "no reference image configured" per-item failure now releases the lease
    (`release_now`) before returning `item_failed` (`next_step_ms=0`).
  - Outcome handling after `generate.generate_one`:
    - `RateLimited`: unchanged item/pacer handling, then `keypool.release(db, key_hash,
      wait_s)`, then `keypool.wait_ms(db, user.id)` — the returned `retry_after_ms`/
      `next_step_ms` is `max(pool_wait, 250)`, falling back to `wait_s` only if no other key
      exists — so the lane waits for the soonest free key, not this key's own backoff.
    - `AuthFailure`: item back to QUEUED; `keypool.disable(db, key_hash, str(e)[:300])`; logs
      `f"API key {key_hint} disabled: {e}"` (hint only, never the key); `remaining_keys =
      keypool.enabled_count(...)` — `0` keeps the existing whole-job `failed` path, otherwise
      returns `waiting` (`retry_after_ms=250`, `next_step_ms=250`,
      `lanes=keypool.lane_count(remaining_keys)`) and the job stays RUNNING.
    - `NoImage`: unchanged attempts/fallback-ladder logic; fetches
      `pace_delay = (await pacer.get_or_create(db, key_hash)).delay_s`, releases the lease at
      that delay, returns `item_failed` with `next_step_ms=0`.
    - success: unchanged storing logic; `keypool.release(db, key_hash, next_delay_s)` after
      `pacer.on_success`; returns `generated` with `next_step_ms=0`.
  - Bottom `except Exception:` safety net adds `keypool.release_now(db, key_hash)` before
    re-raising, alongside the existing "item back to QUEUED" behaviour.
- `backend/app/routers/jobs.py`:
  - `step_job`: drops the `gemini_key_enc` check and `decrypt(...)` call; calls
    `stepper.generate_step(db, job, shop, user)` directly (the "no enabled key" case is now
    handled inside the pool, as `waiting`/`failed`, not a 400 here).
  - `create_job` (EXTRACT/CLASSIFY): replaces the `gemini_key_enc` check + `decrypt(...)`
    pair with `api_key = await keypool.pick_any(db, user.id)` (raises `no_api_key` itself).
  - Removed the now-unused `app.crypto.decrypt` import; added `from app.engine import
    keypool`.
- `backend/app/routers/shops.py`:
  - `upload_reference`: `api_key = await keypool.pick_any(db, user.id)` replaces
    `require_gemini_key(user)`.
  - Removed `require_gemini_key` from the `app.auth` import (still defined in `app/auth.py`,
    unused there now but outside this task's Write-set); added `from app.engine import
    keypool`.

## Discoveries
- `keypool.disable`, `keypool.release`, `keypool.release_now`, and `keypool.lease` each
  commit internally (T02's design), so several of the explicit `await db.commit()` calls this
  task's outcome branches make are on top of an already-committed session — harmless
  (matches the existing codebase's "commit liberally" pattern, e.g. `log()`), not removed to
  stay minimal-diff.
- `job.api_key_hash` is now set unconditionally on every successful lease (was previously
  only set once, `if not job.api_key_hash`), per the brief's "records the LAST key used"
  framing — this is an intentional behavior change, not an oversight.
