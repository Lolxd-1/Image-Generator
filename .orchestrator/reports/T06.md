# T06: frontend API layer and the N-lane generate loop

## What was implemented
- `frontend/src/api/types.ts`: added `ApiKey`, `AddKeyPayload`, `UpdateKeyPayload`,
  `ShopStorage`, `StorageUsage`, `PurgeResult` mirroring `backend/app/schemas.py`'s
  `ApiKeyOut`/`ApiKeyIn`/`ApiKeyPatch`/`ShopStorageOut`/`StorageUsageOut`/`PurgeResultOut`.
  `MeResponse` gained `key_count`/`enabled_key_count`; `StepResult` gained
  `next_step_ms: number`, `key_hint: string | null`, `lanes: number`. `StepStatus` untouched.
- `frontend/src/api/hooks.ts`: added `qk.keys`, `qk.storage`, `qk.shopStorage(id)`, and the
  hooks `useApiKeys`, `useAddApiKey`, `useUpdateApiKey`, `useDeleteApiKey`, `useTestApiKey`
  (all against `/auth/keys...`), `useStorageUsage` (`GET /storage`), `useShopStorage(shopId)`
  (`GET /shops/{id}/storage`, enabled only when `shopId`), `usePurgeShopImages`
  (`POST /shops/{id}/purge-images`), `useDeleteShop` (`DELETE /shops/{id}`). Invalidations
  exactly as specced: key mutations -> `qk.keys` + `qk.me`; purge -> `qk.storage`,
  `qk.shopStorage(id)`, `["shops", id, "items"]`, `qk.shop(id)`; delete shop -> `qk.shops` +
  `qk.storage`.
- `frontend/src/lib/generateLoop.ts`: rewritten internals to run `lanes ?? 1` (capped at 6)
  independent lanes sharing one state object, per Steps 3-4 of the brief:
  - `runningRef` is now the whole-loop RUN guard; each lane has its own entry in
    `laneAliveRef`/`laneInFlightRef`/`laneTimersRef` (all refs, no per-lane React state).
  - `start()` launches lane `i` after `i * 300ms` via `launchLane`.
  - Each lane's next wait is `result.next_step_ms ?? <old fallback>` (`next_delay_ms` for
    generated/item_failed, `retry_after_ms` for rate_limited/waiting), then
    `normalizeWait()` floors any non-zero wait to 250ms while leaving 0 as "immediately".
  - `complete`/`failed` calls `stopAll()` (every lane + every timer).
  - `job_not_running` `ApiError`: `setError(null)` + `stopAll()`, silently, per R4. Any other
    per-lane error calls `stopLane(i)`; if that was the last alive lane, sets `error` and
    calls `stopAll()`.
  - `reconcileLanes(result.lanes)` runs on every continuing response: if the server's `lanes`
    exceeds the current alive count, missing indices below the new target are launched
    (staggered by 300ms among themselves); a lane whose own index is `>= target` stops
    itself instead of scheduling another step, so shrinking never cuts off a request
    mid-flight.
  - `done`/`failed`/`remaining` still just mirror the latest response (no client accumulation);
    `waitMs` is set on every response, so it naturally reflects whichever lane responded
    last; `backingOff` is still `lastStatus === "rate_limited"`.
  - New state fields returned: `lanes` (alive lane count), `activeLanes` (lanes with a
    request currently in flight), `keyHints` (distinct hints, newest first, capped at 8,
    appended via `addKeyHint` whenever a response carries a non-null `key_hint`).
  - Unmount/`pause()` clear every lane's timer through the same `mountedRef`/`runningRef`
    discipline as before, applied per lane.
  - Top-of-file contract comment rewritten to describe lanes, `next_step_ms`, and the
    `job_not_running` rule; unchanged prose (pause/unmount semantics, done/failed/remaining
    mirroring) kept as-is.

## Tests / verification
No frontend test runner exists in this project (confirmed by the brief); each Test case is a
code-path assertion checked by reading the diff:
- TC1 (5 lanes, staggered ~300ms, never >5 concurrent): satisfied structurally — `start()`
  launches exactly `L` lanes each with its own `inFlight` guard, so at most `L` requests can
  ever be in flight at once.
- TC2 (`next_step_ms: 0` on `generated` schedules immediately, not `next_delay_ms`): `result.next_step_ms ?? result.next_delay_ms ?? 0` uses `??`, so an explicit `0` is kept (not treated as absent); `normalizeWait(0) === 0`.
- TC3 (`job_not_running` stops all lanes, `error === null`): handled in the catch block —
  `setError(null)` then `stopAll()`.
- TC4 (`waiting` with `next_step_ms: 4000` only delays that lane): each lane calls
  `scheduleLane(i, wait)` independently; other lanes' timers are untouched.
- TC5 (`pause()` clears every timer; a late response schedules nothing): `pause()` ->
  `stopAll()` clears `runningRef`, all timers, and `laneAliveRef`; every scheduling path
  (`scheduleLane`, `stepLane`'s own entry) checks `runningRef.current`/`laneAliveRef.current.has(i)` first.
- TC6 (`lanes` defaults to 1): `const L = Math.min(Math.max(1, lanes ?? 1), MAX_LANES)`.

## Discoveries
- `backend/app/routers/storage.py` has no router `prefix`; its routes are mounted directly
  under `/api` in `main.py` (`/storage`, `/shops/{id}/storage`, `/shops/{id}/purge-images`,
  `/shops/{id}` DELETE) — not under an `/api/storage` prefix. Hooks use those literal paths.
- Backend `StepResult.next_step_ms`/`lanes` are non-optional with defaults (`next_step_ms: int
  = 0`, `lanes: int = 1`) and `key_hint: str | None = None` — matches the additive types
  exactly as specced.
