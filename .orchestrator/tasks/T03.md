# T03: key-pool API (/api/auth/keys), pool-aware /me, and the boot-time backfill
Wave: 3 · Deps: T02 · Risk: med · Model: sonnet

## Goal
The operator can list, add (live-validated), rename, enable/disable, test and delete Gemini
keys over HTTP; `/api/auth/me` reports the pool; and an existing single key is migrated into
the pool automatically at boot so nothing breaks on deploy.

## Context
T01 added `ApiKey` and the `ApiKeyOut/In/Patch` schemas; T02 added `app/engine/keypool.py`
with `add_key`, `delete_key`, `disable`, `enabled_count` and `migrate_legacy_keys`. The
existing single-key endpoints (`PUT/DELETE /api/auth/gemini-key`) stay, re-pointed at the
pool, because the Login screen still calls them.

## Contracts
- Produces (routes; the router declares paths RELATIVE to /api and is mounted with the others):
```
GET    /auth/keys                  -> list[ApiKeyOut]      200
POST   /auth/keys      ApiKeyIn    -> ApiKeyOut            201 | 400 auth_failure/validation_failed | 409 conflict | 429 rate_limited
PATCH  /auth/keys/{key_id} ApiKeyPatch -> ApiKeyOut        200 | 404 not_found
DELETE /auth/keys/{key_id}         -> 204                  | 404 not_found
POST   /auth/keys/{key_id}/test    -> ApiKeyOut            200 | 404 not_found
```
- Produces (helper, used by every route in the file):
```python
async def _key_out(db: AsyncSession, key: ApiKey) -> ApiKeyOut
# fills delay_s / next_allowed_at / busy from that key's PaceState row
# (missing row -> delay_s = pacer.RATE_START_DELAY, next_allowed_at = None, busy = False)
```
- Consumes: `keypool.add_key`, `keypool.delete_key`, `keypool.disable`,
  `keypool.enabled_count`, `keypool.migrate_legacy_keys`, `gemini.build_client`,
  `gemini.VISION_MODEL`, `gemini.is_auth_error`, `gemini.is_rate_limit`, `crypto.decrypt`.

## Steps
1. `routers/keys.py`: `router = APIRouter(prefix="/auth/keys", tags=["keys"])`.
2. Extract the live-validation block from `auth.py:put_gemini_key` into a module-level
   helper in `keys.py`:
   ```python
   def _validate_live(key: str) -> None
   ```
   which raises `AppError("auth_failure", "Gemini rejected this API key.", 400)`,
   `AppError("rate_limited", ..., 429)` or
   `AppError("validation_failed", "Could not validate the Gemini key.", 400)` exactly as the
   original does. Never include the raw exception text in the response - it can echo key
   material. Run it in a worker thread (`await anyio.to_thread.run_sync(_validate_live, key)`)
   so a slow validation does not block the event loop; `anyio` is already a dependency
   (see `app/storage.py`).
3. `GET /auth/keys`: the caller's keys ordered by `created_at`, each through `_key_out`.
4. `POST /auth/keys`: strip the key; reject empty with
   `AppError("validation_failed", "Key is empty.", 400)`; `_validate_live`; then
   `keypool.add_key(db, user.id, key, label)` where `label` is `payload.label` stripped, or
   `f"Key {n+1}"` with `n` = the caller's current key count. `add_key` already raises the 409
   for a duplicate - let it through. Respond `201` with `_key_out`.
5. `PATCH /auth/keys/{key_id}`: load the row (404 if missing or not the caller's). Apply only
   the fields that were set. Re-enabling (`enabled=True`) also clears `disabled_reason` and
   the key's `leased_until`. Disabling does NOT touch pace state.
6. `DELETE /auth/keys/{key_id}`: load (404), `keypool.delete_key`, return 204.
7. `POST /auth/keys/{key_id}/test`: load (404), decrypt, `_validate_live`. On success set
   `enabled=True`, `disabled_reason=None`, commit, return `_key_out`. On `AppError` with code
   `auth_failure`, call `keypool.disable(db, key.key_hash, "Rejected by Gemini during test")`
   and re-raise. A `rate_limited` result must NOT disable the key - re-raise it unchanged.
8. `auth.py`: `_me_out` becomes async and derives from the pool:
   ```python
   async def _me_out(db: AsyncSession, user: User) -> MeOut
   ```
   `key_count` = the caller's `api_keys` rows; `enabled_key_count` = enabled ones;
   `has_gemini_key` = `enabled_key_count > 0`; `gemini_key_hint` = the hint of the oldest
   enabled key, else `None`. Update both call sites (`login` returns `LoginOut`, unchanged;
   `me` returns `_me_out`). `login` must keep returning `LoginOut(user=...)` exactly as now.
9. `auth.py`: `put_gemini_key` keeps its path and response model but now delegates:
   validate live (import `_validate_live` from `app.routers.keys`), then
   `keypool.add_key(...)`, swallowing the 409 conflict as success (the key is already in the
   pool - that is not an error for this legacy endpoint). It returns
   `GeminiKeyOut(has_gemini_key=True, gemini_key_hint=<that key's hint>)`.
10. `auth.py`: `delete_gemini_key` now deletes EVERY key in the caller's pool (via
    `keypool.delete_key` per row) and also clears `user.gemini_key_enc`/`gemini_key_hint`
    so the boot backfill cannot resurrect them. Still returns 204.
11. `main.py`: import and mount the keys router with the others, and call
    `await keypool.migrate_legacy_keys(session)` in `lifespan`, right after `seed_users`,
    inside the same session block. Wrap it in try/except that logs a warning and continues -
    a backfill failure must not stop the app from booting (unlike seeding, a missing backfill
    leaves the operator able to re-add keys in Settings).

## Test cases
- TC1 (happy): `POST /api/auth/keys {"key":"<valid>"}` with `_validate_live` patched to a
  no-op creates a row and returns 201 with `key_hint` ending in the key's last 4 chars and
  `enabled=True`.
- TC2 (error): the same key posted twice -> 409 with code `conflict`.
- TC3 (error): a key Gemini rejects -> 400 with code `auth_failure`, and NO row is created.
- TC4 (happy): `PATCH {"enabled": false}` then `{"enabled": true}` round-trips and the second
  call clears `disabled_reason`.
- TC5 (happy): `GET /api/auth/me` with two enabled keys reports `key_count=2`,
  `enabled_key_count=2`, `has_gemini_key=true`, and a `gemini_key_hint` matching the older key.
- TC6 (edge): `GET /api/auth/me` with zero keys reports `has_gemini_key=false` and a null hint.
- TC7 (error): `DELETE /api/auth/keys/{random uuid}` -> 404 `not_found`.
These are contract statements, not necessarily automated tests: the suite has no DB fixture,
so DO NOT add one. Verify them by reading the code paths and by the import/route check below.
