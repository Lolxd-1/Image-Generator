# T06: frontend API layer and the N-lane generate loop
Wave: 6 · Deps: T03, T04, T05 · Risk: med · Model: sonnet

## Goal
`useGenerateLoop` drives N concurrent `/step` lanes instead of one, and the API layer exposes
the key-pool and storage endpoints as typed hooks.

## Context
The backend now leases one key per in-flight `/step` call and tells the client how many lanes
to run (`lanes`) and how long THIS lane should wait (`next_step_ms`). Today the loop is
strictly serial: one `runningRef` guard, one timer, one request in flight.

## Steps
1. `types.ts`: add the interfaces above and the additive fields. Keep the existing
   SPEC-GAP comment style. Do not change `StepStatus` - it stays a six-value union.
2. `hooks.ts`: add the query keys and hooks. Mutations invalidate:
   key mutations -> `qk.keys` and `qk.me`; `usePurgeShopImages` -> `qk.storage`,
   `qk.shopStorage(id)`, `["shops", id, "items"]` and `qk.shop(id)`;
   `useDeleteShop` -> `qk.shops` and `qk.storage`.
   Add `useShopStorage(shopId)` too (GET `/shops/{id}/storage`), enabled only when `shopId`.
3. `generateLoop.ts`: rewrite the internals as L independent lanes sharing one state object.
   Required behaviour:
   - `start()` starts `L = lanes ?? 1` lanes. A lane is identified by its index; per lane
     keep its own `inFlight` flag and its own timer handle (arrays or a `Map` held in refs).
     The existing single `runningRef` becomes the RUN guard (is the loop running at all);
     each lane additionally guards against double-stepping itself.
   - Lanes start staggered by `i * 300ms` so K requests do not hit the server in the same
     millisecond and fight for the same first key.
   - After a response, the lane waits `result.next_step_ms` (falling back to the existing
     rules when the field is absent: `next_delay_ms` for generated/item_failed,
     `retry_after_ms` for rate_limited/waiting), floored at 250ms for a non-zero wait and 0
     allowed to mean "immediately", then steps again.
   - `complete` or `failed` stops the WHOLE loop (every lane, every timer), as today.
   - NEW (R4): an `ApiError` with `code === "job_not_running"` means another lane already
     completed the job - stop the whole loop silently, do NOT set `error`. Any other error
     stops that ONE lane; if it was the last running lane, stop the loop and set `error`.
   - If the server reports a `lanes` value larger than the number currently running and the
     loop is running, spin up the extra lanes (a key was added mid-run); if it reports fewer,
     let the surplus lanes stop after their current step. Cap at 6.
   - `done`/`failed`/`remaining` still mirror the LAST server response (they are server
     counters, so a later response supersedes an earlier one - do not accumulate client-side).
   - `waitMs` reports the wait of the lane that most recently responded; `backingOff` stays
     `lastStatus === "rate_limited"`.
   - Unmount and `pause()` clear every lane's timer and prevent any in-flight response from
     scheduling more work - the existing `mountedRef`/`runningRef` pattern, applied per lane.
4. Update the contract comment at the top of `generateLoop.ts` to describe lanes, the
   `next_step_ms` field and the `job_not_running` rule. Keep the existing prose for everything
   that has not changed.

## Test cases
There is no frontend test runner in this project. Each case is a code-path assertion to be
satisfied and checked by reading the diff; `npx tsc --noEmit` is the automated gate.
- TC1 (happy): `useGenerateLoop(id, 5)` with `start()` issues 5 `/step` posts staggered
  ~300ms apart and never more than 5 concurrently.
- TC2 (happy): a `generated` response with `next_step_ms: 0` schedules that lane's next step
  immediately (a 0ms timeout), not after `next_delay_ms`.
- TC3 (error, R4): a `job_not_running` `ApiError` on one lane stops all lanes with
  `error === null`.
- TC4 (edge): `waiting` with `next_step_ms: 4000` makes only that lane wait 4s; other lanes
  keep working.
- TC5 (edge): `pause()` mid-run clears every pending lane timer; a response arriving after
  `pause()` schedules nothing.
- TC6 (edge): `lanes` defaults to 1 when the argument is undefined, preserving today's
  behaviour for any caller that has not been updated.
