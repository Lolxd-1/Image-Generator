# T05: storage usage, "free up space" purge, and delete-catalog
Wave: 5 · Deps: T01 · Risk: high · Model: sonnet

## Goal
The operator can see how much of the 1 GB Supabase budget each shop uses, delete a shop's
generated dish images to reclaim space without losing the catalogue data, and delete a whole
shop with every object and row it owns.

## Context
Storage is a 1 GB free tier and dish images are ~1024px JPEGs at quality 100, so a few shops
fill it. The zip download already exists (`GET /api/shops/{id}/images.zip` in
`routers/images.py`) - this task adds the measuring and deleting half. T01 added
`StorageUsageOut`, `ShopStorageOut` and `PurgeResultOut`.

## Contracts
- Produces (storage.py, on the Protocol and BOTH implementations):
```python
async def delete_many(self, keys: list[str]) -> None
# Supabase: one `remove([...])` call per batch of 100, in a worker thread, ignoring
# per-object "not found" errors. Local: unlink each existing path.
```
- Produces (routers/storage.py) - pure helpers first, so they can be unit-tested with no DB:
```python
BUDGET_BYTES = 1_073_741_824

@dataclass(frozen=True)
class StoredObject:
    key: str
    kind: str          # "dish" | "menu" | "reference" | "item_ref" | "export"
    bytes_len: int

def summarise(objects: Sequence[StoredObject]) -> dict[str, tuple[int, int]]
    # kind -> (count, bytes)
def purge_plan(objects: Sequence[StoredObject]) -> list[str]
    # storage keys to delete for a "free up space" purge: kind == "dish" ONLY
def delete_plan(objects: Sequence[StoredObject]) -> list[str]
    # storage keys to delete for a full catalog delete: every object, deduplicated,
    # order preserved
```
- Produces (routes; paths RELATIVE to /api):
```
GET    /storage                     -> StorageUsageOut
GET    /shops/{shop_id}/storage     -> ShopStorageOut
POST   /shops/{shop_id}/purge-images -> PurgeResultOut
DELETE /shops/{shop_id}             -> 204
```

## Steps
1. `storage.py`: add `delete_many` to the `Storage` Protocol, `SupabaseStorage` and
   `LocalStorage`. Supabase's client takes a list: `self._client.storage.from_(bucket).remove(batch)`.
   Chunk at 100 keys, run each chunk through `anyio.to_thread.run_sync` like the other
   methods, and swallow a per-batch exception after logging a warning (a missing object must
   not abort a delete that has already removed the DB rows' reason to exist). Add a module
   logger for that warning.
2. `routers/storage.py`: `router = APIRouter(tags=["storage"])` (no prefix - it serves both
   `/storage` and `/shops/...`).
3. Write the three pure helpers exactly as in Contracts. `summarise` returns every kind it
   sees; callers map missing kinds to zero.
4. `_collect(db, shop_id) -> list[StoredObject]`: three queries, no N+1 -
   - `images`: `select(Image.storage_key, Image.kind, Image.bytes_len).where(Image.shop_id == shop_id)`
   - `menu_uploads`: `select(MenuUpload.storage_key)` - these rows have no byte count, so
     record `bytes_len=0` and count them; note in a comment that menu photos are bounded at
     1600px/q92 by `shops.py:_prepare_jpeg` and are not the budget problem dish images are.
   - `exports`: `select(Export.storage_key)` - `bytes_len=0` likewise.
5. `GET /shops/{shop_id}/storage`: 404 if the shop is missing; build `ShopStorageOut` from
   `summarise(_collect(...))` with `total_bytes` = the sum of the parts.
   `reference_bytes` covers BOTH `reference` and `item_ref` image kinds.
6. `GET /storage`: every shop (including archived ones), each through the same summary, plus
   `total_bytes` across all of them and `budget_bytes = BUDGET_BYTES`. Use grouped queries -
   one `SELECT ... GROUP BY shop_id, kind` over `images` plus one count query each for
   `menu_uploads` and `exports` - never a query per shop (see `routers/shops.py:list_shops`
   for the pattern this project already uses).
7. `POST /shops/{shop_id}/purge-images`: 404 if missing. Refuse with
   `AppError("conflict", "A job is running for this shop.", status=409)` when a RUNNING job
   exists for the shop - deleting images out from under a generate run corrupts it. Then:
   - collect the shop's `Image` rows with `kind == dish`
   - `UPDATE items SET image_id = NULL WHERE shop_id = :s AND image_id IN (...)` first, so the
     FK does not block the delete
   - `await get_storage().delete_many(purge_plan(...))`
   - delete those `Image` rows
   - commit, return `PurgeResultOut(deleted_images=n, bytes_freed=sum(bytes_len))`
   Item statuses are deliberately left alone: a `hosted` item keeps its imgbb URL and still
   exports; a `generated` item simply no longer has local bytes. Say so in a comment.
8. `DELETE /shops/{shop_id}`: 404 if missing; the same 409 guard for a RUNNING job. Then, in
   this exact order:
   - `delete_many(delete_plan(_collect(...)))` - blobs first; an orphaned blob is worse than
     an orphaned row because nothing in the app can find it again
   - null the FKs that would block row deletion: `shops.reference_image_id = NULL`,
     `items.image_id = NULL`, `items.manual_ref_image_id = NULL`, `images.item_id = NULL`
     (all scoped to this shop), then `flush()`
   - delete rows: `job_events` (by `job_id IN (SELECT id FROM jobs WHERE shop_id = :s)`),
     `jobs`, `exports`, `images`, `items`, `menu_uploads`, then the `shops` row
   - commit; return 204
9. `main.py`: add the storage router to the mounting tuple.

## Test cases
`backend/tests/test_storage_usage.py`, pure functions only (the suite has no DB fixture - do
not add one):
- TC1 (happy) `test_usage_sums_by_kind`: a mixed list of `StoredObject`s -> `summarise`
  returns the right (count, bytes) per kind.
- TC2 (happy) `test_purge_plan_lists_only_dish_keys`: a list containing dish, menu, reference
  and export objects -> `purge_plan` returns exactly the dish keys, in input order.
- TC3 (happy) `test_delete_plan_covers_every_object`: -> `delete_plan` returns every key once,
  in input order, including duplicates collapsed.
- TC4 (edge) `test_plans_on_empty_input`: both plans return `[]` and `summarise` returns `{}`.
- TC5 (edge) `test_summarise_ignores_none_bytes`: an object whose `bytes_len` is 0 still
  counts toward its kind's count.

## Notes
- `ImageKind` values are lowercase strings (`"dish"`, `"menu"`, `"reference"`, `"item_ref"`).
  `Image.kind` is stored as that string.
- `MenuUpload` and `Export` rows carry no `bytes_len`; counting them at 0 bytes is deliberate
  and must be stated in a comment so a future reader does not think it is a bug.
